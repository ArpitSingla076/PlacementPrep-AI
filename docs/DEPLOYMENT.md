# Deployment

Frontend on **Vercel** (static Vite build), API on **Render**, database on **MongoDB Atlas**.
**None of this was deployed or tested from the build environment.** `render.yaml`, `client/vercel.json` and the CI workflow are standard configurations written to be reviewed, not verified.

## 1. Atlas
1. Create a cluster, a database user, and allow your API host's egress IPs under *Network Access* (Render free instances have changing IPs; `0.0.0.0/0` is the usual compromise. Use a strong database password and a dedicated user if you do that).
2. Copy the connection string into `MONGODB_URI`.
3. Create the vector index: see [ATLAS_VECTOR_SEARCH.md](ATLAS_VECTOR_SEARCH.md).

## 2. API on Render
- Use `render.yaml` (Blueprint) or create a Node web service with root `server`, build `npm ci`, start `npm start`, health check `/api/health`.
- Set the secrets in the dashboard (`MONGODB_URI`, `GEMINI_API_KEY`, `LLM_MODEL`, `EMBEDDING_MODEL`, `EMBEDDING_DIMENSIONS`, `CLIENT_URL`). `JWT_SECRET` can be generated by Render.
- Free instances sleep when idle: the first request after a pause is slow, and in-memory quotas and rate limits reset on restart. Background document embedding is lost on a restart; the server marks such documents as failed on boot so they can be re-uploaded.
- Run `npm run ai:check:full` locally with the same key and model before going live.

## 3. Frontend on Vercel
Import the repo with root `client`, framework Vite. `client/vercel.json` rewrites all routes to `index.html` (single-page app). Then choose how the browser reaches the API:

| Option | How | Trade-offs |
|---|---|---|
| **A. Same site (recommended)** | Custom domains under one registrable domain, e.g. `app.example.com` (Vercel) and `api.example.com` (Render). `COOKIE_SAMESITE=lax`, `CLIENT_URL=https://app.example.com`, `VITE_API_URL=https://api.example.com/api` | Needs a domain. Cookies are first-party, so browser third-party-cookie blocking does not apply. |
| B. Cross-site | Default `*.vercel.app` and `*.onrender.com` domains. `COOKIE_SAMESITE=none` (cookie becomes `Secure`), `VITE_API_URL=https://<api>.onrender.com/api` | No domain needed, **but** browsers that block third-party cookies (Safari, increasingly Chrome) can break sign-in. |
| C. Vercel rewrite | Add `{ "source": "/api/:path*", "destination": "https://<api>.onrender.com/api/:path*" }` to `vercel.json`, leave `VITE_API_URL` empty, `COOKIE_SAMESITE=lax` | Same-origin for the browser. **Unverified:** the platform's proxy timeout may be shorter than a slow AI request (analysis can take up to about a minute). Check the current limits before choosing this. |

In every option `CLIENT_URL` must equal the frontend's exact origin: it drives CORS and the CSRF Origin check.

## 4. Checklist before sharing the URL
- [ ] `GET /api/health` returns `{"status":"ok"}`.
- [ ] Register, sign in, reload (session persists), sign out.
- [ ] `/api/ai/status` shows the model and embedding model as configured.
- [ ] Atlas index shows **ACTIVE**; upload a small PDF in Documents and ask a question.
- [ ] Read the Gemini API terms for your plan before real resumes or notes are used.

## Troubleshooting: "Cannot reach the server" / "blocked by CORS policy"
These browser messages all mean *the browser got no usable answer from the API*. Work through them in this order:

1. **Is the API running?** Open `https://<your-api>.onrender.com/api/health` in a browser (the first request after idle can take up to a minute on the free plan).
   - A JSON reply with `"status":"ok"` means it is running, and it lists `allowedOrigins`. **That list must contain your frontend's address exactly** (for example `https://my-app.vercel.app`).
   - An error page, or no reply, means the API is down. Open Render > Logs. A line starting `[fatal]` names the reason. A crashed API sends no CORS headers, so the browser reports a CORS error even though CORS is not the real problem.
2. **Did the last deploy succeed?** Render keeps serving the *previous* version when a new deploy fails. Check Render > Events for "Deploy failed".
3. **Does `allowedOrigins` match?** If not, fix `CLIENT_URL` on Render. It accepts one address or several separated by commas, and ignores quotes, spaces and trailing slashes.
4. **Render logs show `[cors] blocked a request from <address>`**: that address is not in `CLIENT_URL`. Add it.
5. **Sign-in works but you are logged out on reload**: set `COOKIE_SAMESITE=none` and `NODE_ENV=production`, and test in a normal Chrome or Edge window.
6. **Frontend still calls the wrong API**: `VITE_API_URL` is read at *build* time. Change it, then Redeploy on Vercel.

## Recommended: let Vercel forward /api to the server (same-site mode)
`client/vercel.json` forwards every `/api/...` request to the Render server. When the frontend is built **without** `VITE_API_URL`, the browser only ever talks to the Vercel address, so there is no CORS at all and the login cookie is a normal first-party cookie that every browser accepts.
1. In Vercel > Settings > Environment Variables, **delete `VITE_API_URL`**, then Redeploy.
2. In Render set `TRUST_PROXY_HOPS=2` (Vercel + Render are both in front of the app) and, optionally, `COOKIE_SAMESITE=lax`.
3. Keep `CLIENT_URL` equal to the Vercel address.
Unverified: Vercel's proxy may cut off requests that take very long (resume analysis can take about a minute). If AI requests fail this way, set `VITE_API_URL` back to the Render address (direct mode still works).

## The "Connection check" page
Open `https://<your-site>/status` at any time. It contacts the server directly, bypassing every cache, and says in plain words whether the server is asleep, blocking this website, missing its database, or fine.

## Reading the /status page
It runs three checks: (1) a direct request to the server, (2) the same request ignoring CORS permissions (succeeds if *any* reply arrives), and (3) a same-site request through this website's own `/api` forwarding. The combination tells you where the break is:
- **1 fails, 2 fails, 3 works**: your browser or network cannot connect to the server directly. Delete `VITE_API_URL` in Vercel and redeploy to use the same-site path.
- **1 fails, 2 works**: the server answers, but not with CORS permission (the reply is from the hosting platform, or `CLIENT_URL` is wrong). Check Render > Logs for a `[cors] blocked` line.
- **everything fails**: asleep, not running, or blocked by a network. Test on a phone with mobile data.
Render's logs now include `origin=<website>` on every request line, so you can see whether the website's calls arrive at the server at all.
